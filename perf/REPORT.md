# Отчёт: производительность UI LlamaPort

Дата: 2026-11-18. Устройство: HONOR RMO-NX1, Android 13 (SDK 33), arm64-v8a, 8 ядер, 7,3 ГБ RAM.  
Сборка: release (`isMinifyEnabled=true`), подписана debug-ключом, `<profileable android:shell="true" />` для Perfetto/simpleperf.  
Дисплей: 120 Гц (active mode 2), 1080×2400. Яркость 128, системные анимации 1.0, экран включён.  
Методика: `am force-stop` перед каждым прогоном, пауза до температуры 35,6–37,4 °C (после разогрева плато ~37 °C), 3 повтора (S1 — 5), медианы.  
`dumpsys gfxinfo` + `framestats`; на этом Android `framestats` отдаёт только последние 10 кадров, поэтому перцентили и доля медленных кадров посчитаны по полной гистограмме `gfxinfo`.  
Порог 8,3 мс — 120 Гц; 16,7 мс — 60 Гц. Android-метрика «Janky frames» считает по 16,7 мс.

## 2. Варианты для атрибуции

| Вариант | Повторов | Кадров | Janky, % | p50 / p90 / p95 / p99, мс | >16,7 мс | >8,3 мс | CPU main / Render, % |
|---|---:|---:|---:|---|---:|---:|---|
| S3 plain text | 3 | 3614 | 3.46 | 8 / 13 / 16 / 21 | 170 | 1330 | 38.1 / 57.1 |
| S3 без анимаций (робот+курсоры+точки) | 3 | 580 | 62.16 | 21 / 30 / 32 / 36 | 353 | 451 | 22.2 / 7.4 |
| S5 без анимаций | 1 | 380 | 74.74 | 25 / 31 / 32 / 34 | 255 | 334 | 16.9 / 5.7 |

Ключевые наблюдения:  
- **S3_plain** (без Markdown, обычный `Text`) даёт лишь ~15% меньше jank (3,46% против 4,05%) и p90 13 против 14 мс. Значит парсинг/блоки Markdown — не главный источник; основной вклад даёт раскладка/отрисовка растущего текста и широкая рекомпозиция.  
- **S3_no_anim** (выключены пульс точки модели, курсоры, точки thinking и анимация robot avatar): main CPU 39,2→22,2%, RenderThread 57,4→7,4%, но кадров 3607→580 (19 fps), jank 62%. Это не «исправление»: анимации генерируют дешёвые кадры и держат 120 Гц. Они стоят ~17 п.п. main CPU и ~50 п.п. RenderThread, но не являются причиной медленных кадров обновления текста.  
- **S3_publish15** (тот же поток 25 ток/с, публикация 15 Гц) **хуже** S4 (9,33% против 8,20%, p90 16, p99 28): крупные пачки текста дают больший layout/draw за кадр. Буферизацию нужно делать по vsync-кадру, а не фиксированными 66 мс.  
- **S2_no_logo** — статичный экран, всего 5–6 кадров за 30 с; метрика jank к нему неприменима.

## 4. Топ-5 горячих мест

1. **Полный re-parse и широкая рекомпозиция Markdown на каждый токен.**  
   `app/src/main/java/com/llamaport/app/Markdown.kt:80` — `val blocks = remember(text) { parseMarkdown(text) }`; при каждом изменении текста создаётся новый список блоков, `blocks.forEachIndexed` перекомпоновывает поддерево. `Messages.kt:227` (`splitThinking`), `Messages.kt:289` (`AssistantMessage`), `Messages.kt:358` (`MarkdownText`).  
   Цифры: S3 p99 22 мс, 166/3607 кадров >16,7 мс; самая длинная рекомпозиция 15,71 мс с 18 `Compose:recompose`; S3_plain снижает jank до 3,46% и p99 до 21 мс — то есть Markdown-слой даёт ~10–15%, но не является единственной причиной.  
2. **Состояние на каждый токен: копирование списка сообщений и два обновления StateFlow (текст + метрики).**  
   `ChatViewModel.kt:363` (`updateMessages`), `ChatViewModel.kt:387` (`updateMessageMetrics`), `ChatViewModel.kt:414` (`appendToMessage`), вызовы из `onToken`/`onGenerationProgress` около `ChatViewModel.kt:1500–1560`.  
   Цифры: main CPU 39,2% при 10 ток/с и 50,0% при 25 ток/с; jank 4,05→8,20%. Публикация 15 Гц дала 9,33% — хуже, значит проблема не в частоте как таковой, а в размере и стоимости одного обновления.  
3. **Раскрытый live-блок размышлений.**  
   `Messages.kt:652` (`ThinkingBlock`), `Messages.kt:721` (`MarkdownText(thinking, streaming)`), `Messages.kt:739` (`ThinkingDots`). Пока `parts.answer.isEmpty()`, блок раскрыт и перерисовывается на каждом токене; у LFM3 это большая часть генерации.  
   Цифры: S5 (реальная LFM3) — RenderThread 67%, main 45%, `animation` 23,4%, `Recomposer:recompose` 12,3%; при этом обновлений всего 7,7/с. S3 trace на первых 8 с — тоже почти весь thinking-блок: RenderThread 45%, `animation` 18,2%.  
4. **Анимации, которые держат полный кадр окна на 120 Гц.**  
   `HomeChrome.kt:121` (пульс точки модели), `Messages.kt:533` (курсор), `Markdown.kt:199` (курсор Markdown), `Messages.kt:739` (точки thinking), `ui/robot/RobotAvatar.kt:86` (пульс аватара).  
   Цифры: выключение всех этих анимаций — main CPU 39,2→22,2%, RenderThread 57,4→7,4%, кадры 3607→580. Анимации стоят дорого, но именно они дают плавность между обновлениями текста; отключать их нельзя, нужно делать дешевле/реже.  
5. **Отрисовка текста и обмен буферами (RenderThread/GPU).**  
   `Markdown.kt:108+` (`MdBlockView`, `CodeBlock`), Compose `Text`/`BasicText`; `Messages.kt:289`.  
   Цифры: `RenderThread Drawing` 45% (S3) и 67% (S5); `postAndWait` 23% S3 и 23,5% S5; simpleperf S3: `libhwui.so` 18,4%, GPU-драйвер 8,6%, app odex (Compose/UI) 27,6%, `libart` 12,8%.  

Дополнительно: S8 (листы) — p99 14 мс, 1,24% jank, не горячее место; S9 — p99 14 мс, 0,69%; S6 — 0,05% jank, p99 6 мс.  
S1 — медиана старта 270 мс, p99 150 мс в 56 стартовых кадрах; для холодного старта это нормально, оптимизация не приоритетна.

## 5. Атрибуция: UI или конкуренция с инференсом

- **Не конкуренция за CPU.** В S3/S5 main Runnable 7,4%/2,2%, main Running 36%/45%; потоки инференса не отбирают у main квант. S5 (реальная генерация) имеет jank **1,66%**, меньше, чем fake 10/25 ток/с (4,05%/8,20%), потому что LFM3 выдаёт 7,7 ток/с и UI обновляется реже. Если бы виноват был инференс, S5 был бы хуже fake, а не лучше.  
- **Виноват UI-путь стриминга**: обновление текста, рекомпозиция поддерева сообщения и отрисовка растущего текста. Чем выше частота обновлений, тем хуже: 7,7→10→25 ток/с даёт jank 1,66→4,05→8,20%.  
- **S5 тяжелее по RenderThread (67%)**, чем fake (45%), из-за live-thinking и большего объёма текста; это не «инференс съел CPU», а «UI рисует больше».  
- **S2 80,9% jank — ложная тревога**: 13,3 fps тикер робота, p99 21 мс, main/Render по 11%.  
- **S6/S7/S9 гладкие**: скролл и раскрытие thinking не являются проблемой; S7 лёгкий потому, что при ручном скролле растущее сообщение уходит из вьюпорта, а не потому, что стриминг дешёвый.

## 6. Предлагаемые исправления (не применены)

1. **Инкрементальный рендер стриминга.** Не парсить весь Markdown заново и не перекомпоновывать все блоки: держать стабильные завершённые блоки, обновлять только хвостовой блок; для простого текста — `BasicText`/`AnnotatedString`, добавлять в конец без пересоздания блоков. Ожидаемо: p99 22→16–18 мс, jank 4,05→2%, при 25 ток/с 8,2→4–5%, main CPU −10–15%.  
2. **Обновление состояния по кадру, а не по токену.** Один `withFrameNanos`-коалесcер: накопить токены, опубликовать один раз за vsync; метрики скорости обновлять 4–5 раз/с отдельным state. Не делать фиксированные 15 Гц (данные показали ухудшение). Ожидаемо: main CPU −5–10%, jank при 25 ток/с −2–3 п.п.  
3. **Ограничить live-thinking.** Раскрытый блок размышлений держать фиксированной высоты/последние N строк, без Markdown-перерисовки всего текста; точки/пульс аватара — статичные во время стриминга. Ожидаемо для S5: RenderThread −20–30%, main animation −50%, p99 21→16–17 мс.  
4. **Сделать анимации дешевле, не убирая их.** Пульс точки модели/курсоры/точки thinking перевести на 30–60 Гц или отдельный слой, не инвалидировать всё окно на 120 Гц. Ожидаемо: main −5–10%, RenderThread −10–20%; сохранить плавность.  
5. **Снизить стоимость draw.** `drawWithCache`/DisplayList для статичных блоков, не перерисовывать неизменившиеся абзацы/код, уменьшить overdraw. Ожидаемо: RenderThread −10–20%, особенно при длинном ответе.  
6. **S8/листы** — p99 14 мс, не приоритет; при желании убрать анимацию открытия списка моделей на время сканирования.  
7. **S1** — 270 мс TotalTime, p99 150 мс; при желании вынести восстановление сессии/темы с главного потока, но выигрыш меньше, чем в стриминге.

Трассы S3/S6 короче 20 с из-за 32 МБ буфера; S5/S7 пересняты с 128 МБ.
