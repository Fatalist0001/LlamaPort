# Идея: базовый кэш системного промпта и инструкций инструментов

**Статус:** отложено — делать после этапов 7–8 редизайна (`REDESIGN.md`), отдельной задачей.
**Дата:** 2026-11-15
**Зачем:** убрать повторную обработку неизменного префикса промпта (системный промпт + инструкции инструментов) перед первым сообщением и при переключении чатов.

---

## 1. Проблема

Сейчас кэш промпта живёт только в RAM сессии модели и требует, чтобы сохранённые токены целиком
были префиксом нового промпта.

Код:

- `app/src/main/cpp/llama_jni.cpp` — `Session::prompt_cache`, `Session::full_cache`,
  `save_cache_slot()`, `try_restore_cache()`;
- порядок восстановления в `generate(...)`: сначала `full_cache`, затем `prompt_cache`;
- `try_restore_cache()` выбрасывает слот, если `common_prefix_len(slot.tokens, tokens) != slot.tokens.size()`.

Следствия:

1. **До первого сообщения кэша нет вообще** — система и инструкции инструментов считаются с нуля.
2. **При переключении чатов весь кэш пропадает**: новый префикс расходится со старым, условие
   «полный префикс» не выполняется, и заново обрабатывается даже системная часть.
3. Инструкции инструментов (`ToolRegistry.prompt()`, `Tools.kt`) — это ~1.4 КБ текста, примерно
   300–450 токенов. При измеренной скорости обработки промпта 12–25 tok/s это **15–30 секунд**
   на первом сообщении после загрузки модели/запуска приложения.

---

## 2. Идея

Добавить третий слот **`base_cache`**, содержащий только базовый блок:

```
system prompt
+ инструкции инструментов (extraSystem)
+ инструкция про размышления (если включён бюджет)
```

Этот блок для данной модели и данных настроек **всегда одинаковый** и всегда является префиксом
любого промпта этой сессии.

Слот:

- снимается **во время первого же префилла** (не добавляет вычислений — эти токены всё равно
  считаются в первом сообщении);
- сохраняется на диск и переиспользуется между запусками приложения и переключениями чатов;
- инвалидируется по отпечатку модели и настроек.

---

## 3. Как строить базовый слот

### 3.1. Граница базового блока

Нативно нужно знать, где кончается системная часть. Вариант:

1. Kotlin рендерит системный блок отдельно:
   `applyTemplate(["system"], [systemText], addAssistant = false)` → байты;
2. передаёт этот текст (или его токены) в `generate(...)` (новый параметр) либо в отдельный
   JNI-метод;
3. native вызывает `llama_tokenize` для обоих текстов и считает
   `L = common_prefix_len(baseTokens, promptTokens)`.

`L` может оказаться на 1–2 токена меньше длины `baseTokens` из-за BPE-склейки на границе
(токен может захватывать начало следующей секции). Это нормально: префикс просто будет чуть короче.

### 3.2. Снятие состояния при первом префилле

В цикле обработки промпта (`llama_jni.cpp`, ветка текстового промпта, `n_chunk = 32..256`):

1. обработать токены `[0, L)`;
2. `save_cache_slot(base_cache, ctx, tokens[0..L), …)`;
3. продолжить обычную обработку с `L` (существующий код уже умеет начинать с `prefix_len`,
   позиции продолжаются корректно, т.к. `llama_state_seq_set_data` восстанавливает `n_past`).

### 3.3. Порядок восстановления

```
if (try_restore_cache(full_cache))   → prefix_len = ...
else if (try_restore_cache(prompt_cache)) → prefix_len = ...
else if (try_restore_cache(base_cache))  → prefix_len = ...
else                                      → prefix_len = 0
```

Базовый слот не удаляется при промахе — он переиспользуется всеми чатами.

## 4. Ключ кэша (обязательно)

Состояние KV зависит не только от файла модели. Ключ (fingerprint) должен включать:

| Компонент | Почему |
|---|---|
| имя + размер + mtime (или хэш) файла модели | другая модель — другие веса/токенизатор |
| наличие/имя mmproj | влияет на шаблон и позиции медиа |
| `n_ctx` | меняет KV-буфер и RoPE-диапазон |
| тип KV (`f16` / `q8_0`) | другое представление ячеек |
| Flash Attention (`auto/on/off`) | меняет раскладку KV |
| шаблон чата (хэш результата `applyTemplate` для system) | другой шаблон — другой текст/токены |
| system prompt (хэш текста) | меняет первые токены |
| промпт инструментов (хэш `ToolRegistry.prompt()`) | ~300–450 токенов |
| `enableThinking` / бюджет размышлений | добавляет/убирает инструкцию в system |
| версия llama.cpp (номер сборки) | формат `llama_state_seq_*` не гарантирован между версиями |

Формат файла: заголовок `magic + formatVersion + fingerprintHash + tokenCount + stateBytes`,
далее сырое состояние `llama_state_seq_get_data`.

При загрузке проверять:

- `fingerprint` совпал;
- `llama_state_seq_set_data(...) != 0`;
- `tokenCount` совпадает с сохранённым.

Любая ошибка → удалить файл, построить заново.

## 5. Где хранить и когда сохранять

- Каталог: `filesDir/prompt_cache/`.
- Файл на пару «модель + настройки»; достаточно 1–2 файлов, старые удалять по LRU.
- Размер: состояние пишет только занятые ячейки, поэтому ~5–15 МБ для 1.7B при q8_0
  (для сравнения: RAM-лимит существующих слотов — 256 МиБ).
- Сохранять **асинхронно после первого префилла**, не блокируя UI и не мешая генерации.

### Чего не делать

**Не прогревать модель сразу после загрузки.** Это те же секунды CPU, только раньше: если
пользователь не отправит сообщение, работа уйдёт впустую (и это лишний нагрев). Снимать кэш
только во время реального первого префилла.

---

## 6. Ожидаемый эффект

| Сценарий | Сейчас | С базовым слотом |
|---|---|---|
| Первое сообщение после запуска приложения | system+tools считаются заново | берутся с диска |
| Первое сообщение после загрузки другой модели | считаются заново | берутся с диска (если fingerprint совпал) |
| Переключение между чатами | промпт целиком | system+tools из слота |
| Обычные ходы в одном чате | уже работает `prompt_cache`/`full_cache` | без изменений |
| Ход после правки/удаления сообщения | промпт целиком | system+tools из слота |

Ожидаемая экономия: **15–30 секунд** на первом сообщении после запуска и при переключении чатов
(при включённых инструментах; без инструментов — меньше, там база почти пустая).

Обычную генерацию это **не ускоряет** — не путать с оптимизацией инференса.

## 7. Ограничения и риски

- **Нестабильный формат состояния** llama.cpp: обязательны версия в ключе и проверка при
  восстановлении.
- **BPE на границе**: базовый префикс может быть на 1–2 токена короче — не ошибка.
- **Рекуррентные модели (LFM3)**: текущая логика принимает только «чистое продолжение»
  сохранённого префикса; базовый слот удовлетворяет этому по построению.
- **Медиа**: сейчас любой путь с mmproj делает `clear_all_caches()`. Базовый слот можно сохранять
  (он стоит до медиа-маркера), но это отдельная проверка; на первом этапе — не трогать.
- **Нативная часть**: изменение затрагивает `llama_jni.cpp`, JNI/AIDL и `LlmService`, что выходит
  за рамки правила редизайна «не трогать инференс/JNI/AIDL». Поэтому — отдельная задача.
- **Память/диск**: 5–15 МБ на файл; при смене `n_ctx`/KV/FA файл перестраивается.
- **Приватность**: в кэше только системный блок, пользовательских данных нет.

## 8. План проверки

1. Включить инструменты, загрузить модель.
2. Замерить базовую линию: время до первого токена и `промпт X tok/s` на первом сообщении.
3. После реализации: в `adb logcat | grep "cache:"` должно появиться
   `prompt: restored N tokens from base cache`.
4. Сравнить первый токен после перезапуска приложения и после переключения чатов.
5. Проверить инвалидацию: изменить system prompt / `n_ctx` / kv type → кэш перестраивается,
   приложение не падает и не восстанавливает чужое состояние.
6. Проверить на `LFM3-1.7B-GSQ-1GB-IQ4_XS_RCO` и на модели с mmproj.
