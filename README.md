# LlamaPort

Android-порт [llama.cpp](https://github.com/ggml-org/llama.cpp) с графическим интерфейсом на Kotlin + Jetpack Compose.
Модель (GGUF) работает полностью на телефоне, без интернета.

## Что внутри

- `llama.cpp/` — исходники llama.cpp **b12129**; в репозиторий не входят, их нужно
  распаковать в эту папку (см. «Подготовка окружения»).
- `app/` — Android-приложение (`com.llamaport.app`).
  - `MainActivity.kt` — точка входа.
  - `ChatViewModel.kt` — состояние чата, сессии, импорт и загрузка моделей, генерация.
  - `ChatScreen.kt` — интерфейс (Compose Material 3).
  - `ChatStore.kt` — сохранение сессий и вложений в `sessions.json`.
  - `Markdown.kt` — лёгкий Compose-рендерер Markdown.
  - `Thinking.kt` — разбор блоков размышлений.
  - `LlamaBridge.kt` — JNI-мост.
  - `src/main/cpp/llama_jni.cpp` — нативная обёртка над C API llama.cpp и `libmtmd`.
- `scripts/build-native.sh` — кросс-сборка `libllama.so`, `libllama-common.so`, `libggml*.so`, `libmtmd.so`, `libquickjs-jni.so` и `libllamaport.so` под `arm64-v8a`.
- `scripts/build-apk.sh` — сборка debug APK.
- `scripts/build-release.sh` — сборка подписанного release APK (R8 + shrinkResources).
- `scripts/gradle.sh` — локальный Gradle 8.9 + JDK 21.
- `.sdk/` — Android SDK/NDK (локальная установка, в репозиторий не входит).
- `toolchain/` — JDK 21 и Gradle 8.9 (локальная установка, в репозиторий не входит).

Скрипты из `scripts/` ищут `ANDROID_HOME`, `GRADLE_USER_HOME` и `JAVA_HOME`
внутри каталога проекта, поэтому ничего не пишется в домашнюю папку.

## Подготовка окружения

В репозитории нет бинарных зависимостей — их нужно положить локально (все эти
каталоги перечислены в `.gitignore`):

1. **JDK 21** — распаковать в `toolchain/jdk` (Adoptium Temurin 21).
2. **Gradle 8.9** — распаковать в `toolchain/gradle-8.9`
   ([gradle.org/releases](https://gradle.org/releases/)).
3. **Android SDK** — `platforms/android-35`, `build-tools/35.0.0`,
   `platform-tools` и `ndk/28.2.13676358` в `.sdk/`.
4. **Исходники llama.cpp b12129** — в `llama.cpp/`:
   ```bash
   curl -L https://github.com/ggml-org/llama.cpp/archive/refs/tags/b12129.tar.gz \
     | tar -xz -C llama.cpp --strip-components=1
   ```
5. **QuickJS** уже лежит в репозитории: `third_party/quickjs` (MIT).
6. **Ключ подписи** — `keystore/llamaport-release.jks` и `keystore.properties`
   (не коммитятся, образец полей — ниже).

`keystore.properties`:

```properties
storeFile=keystore/llamaport-release.jks
storePassword=...
keyAlias=...
keyPassword=...
```

Без этого файла `scripts/build-release.sh` не найдёт ожидаемый подписанный APK;
debug-сборка от ключа не зависит.

## Сборка

```bash
./scripts/build-apk.sh
```

Готовый APK: `app/build/outputs/apk/debug/app-debug.apk` (копия —
`LlamaPort-debug.apk` в корне проекта, ~20 МБ).

Release-сборка (минификация R8, подпись ключом из `keystore.properties`):

```bash
./scripts/build-release.sh
```

Готовый APK: `app/build/outputs/apk/release/app-release.apk` (копия —
`LlamaPort-release.apk` в корне проекта, ~11.5 МБ). Keystore лежит в
`keystore/llamaport-release.jks`, параметры подписи — в `keystore.properties`.
Debug и release подписаны разными ключами, поэтому перед установкой release
поверх debug нужно удалить debug-версию (`adb uninstall com.llamaport.app`).
Для локальной проверки release без потери моделей можно собрать
`LLAMAPORT_DEBUG_SIGNING=1 ./scripts/build-release.sh` — APK будет подписан
debug-ключом и установится поверх debug-версии.

Только нативная часть (если менялся `llama_jni.cpp`):

```bash
./scripts/build-native.sh
```

## Установка и запуск

```bash
.sdk/platform-tools/adb install -r app/build/outputs/apk/debug/app-debug.apk
.sdk/platform-tools/adb shell am start -n com.llamaport.app/.MainActivity
```

Модель можно выбрать через кнопку «Выбрать GGUF-модель» (файл копируется во
внутреннее хранилище приложения). Для автоматического тестирования модель можно
положить сразу в `files/models` (приложение debuggable):

```bash
adb push model.gguf /data/local/tmp/model.gguf
adb shell run-as com.llamaport.app mkdir -p files/models
adb shell "run-as com.llamaport.app cp /data/local/tmp/model.gguf files/models/"
```

## Возможности приложения

- импорт `.gguf` через системный файловый пикер (SAF); `mmproj-*.gguf` рядом с
  моделью подключается автоматически;
- список моделей, загрузка/выгрузка, удаление, индикация vision/audio;
- облачные модели: OpenAI-совместимый провайдер (название, base URL, ключ) в
  отдельном блоке того же меню моделей, «Получить список моделей» через
  `GET /models` или ручное добавление, потоковые ответы и отмена;
- несколько чатов с сохранением истории в `filesDir/sessions.json`: создание,
  переключение, переименование, удаление; история и вложения переживают перезапуск;
- чат с потоковой генерацией и кнопкой остановки; автопрокрутка не мешает читать,
  если пользователь прокрутил вверх, и возвращается кнопкой «вниз»;
- Markdown (заголовки, списки, код, жирный/курсив) и сворачиваемые блоки
  размышлений с количеством символов;
- вложения: изображения и аудио (wav/mp3/flac) через `libmtmd`; изображение
  показывается в сообщении, аудио можно прослушать;
- живая статистика под ответом: во время обработки промпта показывается скорость
  обработки, затем она сменяется скоростью генерации; после завершения остаётся
  кнопка «N токенов», открывающая диалог с полными цифрами (скорость обработки,
  токены промпта, скорость генерации, время);
- текстовый KV-кэш хранит три снимка: системный блок, префикс промпта и
  состояние после генерации (включая видимый ответ); системный блок сохраняется
  на диск и переиспользуется между запусками и чатами, поэтому инструкции
  инструментов не считаются заново; блоки размышлений в контекст не
  возвращаются, поэтому для моделей с `thinking` используется запасной
  prompt-кэш, а для обычных ответов работает полный кэш;
- на главном экране показывается свободная оперативная память
  (`Свободно 2.1 ГБ из 7.3 ГБ`) и обновляется каждые 5 секунд;
- два экрана настроек: «Настройки модели» в боковом меню (контекст, потоки,
  пакет/микробатч, Flash Attention, mmap, тип KV-кэша) и «Параметры генерации»
  по кнопке регулировок слева от «+» (системный промпт, температура, top-p,
  top-k, лимит ответа, бюджет размышлений, инструменты; для активной облачной
  модели — ещё и её совместимость с API);
- оценка памяти под выбранный контекст и красное предупреждение, если модель
  может не поместиться в RAM;
- статистика под ответом: скорость обработки промпта, скорость генерации и число
  токенов;
- чат-шаблон берётся из метаданных модели (`tokenizer.chat_template`) и
  рендерится Jinja-движком llama.cpp (`common/chat`), поэтому каждая модель
  получает свой формат диалога, а не общий угаданный; BOS добавляется ровно один
  раз, начало ответа формирует сам шаблон. Если шаблон отрендерить не удалось,
  используется прежний ограниченный matcher как запасной путь; для LFM3
  по-прежнему поддержаны `<think>`/`</think>`;
- корректная работа с UTF-8: токены склеиваются в нативном коде по границам
  символов.

## Где находятся настройки

- **«Настройки модели»** — прежняя кнопка с шестерёнкой в боковом меню. Здесь
  контекст, потоки генерации и промпта, пакет, микробатч, Flash Attention, mmap
  и тип KV-кэша. Изменения вступают в силу при следующей загрузке модели или
  после нажатия «Перезагрузить модель»; автоматически модель не перезагружается.
  Потоки генерации тоже относятся к этой группе: сейчас они задаются при
  создании native-контекста, а не при отправке каждого запроса.
- **«Параметры генерации»** — кнопка с регулировками слева от «+» в верхней
  панели главного экрана и чата. Здесь системный промпт, пресеты температуры,
  температура, Top-P, Top-K, максимум новых токенов, бюджет размышлений,
  разрешение и выбор инструментов. Для изменения этих параметров перезагрузка
  модели не нужна.
- Новый запрос использует актуальные настройки генерации. Уже идущий ответ
  **и все его шаги с инструментами** используют снимок настроек, сделанный при
  отправке. Изменение или отключение инструментов во время ответа влияет только
  на следующий запрос.
- Обе панели редактируют один общий набор настроек; диапазоны значений и
  проверка `микробатч ≤ пакет` не изменены. Разделение экранов не добавляет
  отдельные настройки для каждого чата или сохранение настроек на диск.

## Облачные модели

Кроме локального GGUF приложение работает с любым OpenAI-совместимым API:
`POST {base}/chat/completions` и `GET {base}/models`.

- **Провайдер** задаётся тремя полями: произвольное название, base URL
  (например `https://api.openai.com/v1`) и ключ. Ключ можно оставить пустым —
  для локального сервера без авторизации. Если в адресе нет пути, приложение
  один раз попробует дописать `/v1` и запомнит исправленный адрес.
- **Список моделей**: кнопка «Получить список моделей» заполняет список из
  ответа API. Если провайдер не отдаёт `/models` или отвечает ошибкой, модели
  добавляются вручную — эта возможность доступна всегда.
- Облачные модели живут **отдельным блоком** в том же меню, что и локальные.
  «Загрузка» такой модели — это выбор; ранее загруженная локальная модель при
  этом выгружается, чтобы не занимать память.
- Ответ приходит потоком (SSE), кнопка остановки рвёт соединение сразу.
  Статистика берётся из `usage`, когда API его присылает, иначе оценивается по
  числу дельт. Инструменты работают так же, как с локальными моделями:
  промпт-протокол `<tool_call>` не зависит от бэкенда.
- В этой версии облачные модели принимают **только текст**, без вложений.

### Совместимость параметров

Разные API принимают разные поля, и спецификация OpenAI здесь не гарантия.
Приложение не угадывает формат, а договаривается:

1. Запрос отправляется с параметрами из профиля совместимости провайдера.
2. Если API отвечает ошибкой и в теле назван отправленный параметр
   (`unsupported` / `unknown` / `invalid` / `extra` и т. п.), отключается
   **только этот параметр**, запрос повторяется (до трёх попыток), а результат
   сохраняется в `cloud.json`. Так отключаются `top_k`, `temperature`, `top_p`,
   `max_tokens` (с переходом на `max_completion_tokens`, затем к отсутствию
   поля) и `stream`.
3. Если ошибку не удаётся привязать к параметру, показывается текст провайдера —
   без угадывания.
4. Явная проверка: кнопка ▶ у модели в редакторе или «Проверить API» в
   «Параметрах генерации» отправляет два коротких запроса и печатает отчёт.
   В секции «Совместимость API» те же параметры можно включить или выключить
   вручную.

Настройки загрузки (контекст, потоки, пакеты, Flash Attention, mmap, KV-кэш) к
облачной модели не относятся; экран «Настройки модели» сообщает об этом.

## Технические детали

- облачный слой (`app/src/main/java/com/llamaport/app/cloud/`) работает в
  UI-процессе: `HttpURLConnection` + `org.json`, без новых runtime-зависимостей;
  нативные библиотеки, CMake и AIDL не менялись. Чистая логика (нормализация
  URL, тело запроса, разбор SSE, договорённость о параметрах, хранилище)
  покрыта JVM-тестами: `./scripts/gradle.sh :app:testDebugUnitTest`;
- провайдеры и выбранная облачная модель сохраняются в `filesDir/cloud.json`
  атомарной записью. Ключи не пишутся в логи и исключены из резервных копий и
  переноса на другое устройство (`res/xml/backup_rules.xml`,
  `res/xml/data_extraction_rules.xml`);
- `android:usesCleartextTraffic="true"` включён, чтобы работали self-hosted
  серверы по `http://` в локальной сети. В редакторе провайдера такой адрес
  помечается предупреждением о незашифрованном трафике;
- llama.cpp собран с `BUILD_SHARED_LIBS=ON`, `LLAMA_BUILD_MTMD=ON` и
  `LLAMA_BUILD_COMMON=ON` (без LLGuidance и subprocess), без OpenMP, с
  `GGML_CPU_ARM_ARCH=armv8.2-a+dotprod+fp16` (телефон поддерживает
  dotprod/fp16); `libmtmd.so` и `libllama-common.so` упакованы в APK.
  `libllama-common.so` нужен ради Jinja-движка чат-шаблонов и добавляет около
  4,7 МБ к размеру APK.
- Изображения и аудио декодируются `libmtmd` (`mtmd_helper_bitmap_init_from_buf`,
  stb_image/miniaudio), в промпт подставляется маркер `<__media__>`, а
  `mtmd_helper_eval_chunks` считает M-RoPE и позиции.
- Реальный максимум контекста читается из GGUF (`*.context_length`) и
  показывается как рекомендация: слайдер идёт до 262144, при превышении
  появляется предупреждение. KV-кэш масштабируется для оценки памяти.
- Сессии пишутся в `sessions.json` атомарно и только на контрольных точках, не
  на каждом токене.
- `minSdk 26`, `targetSdk 34`, `compileSdk 35`; ABI — `arm64-v8a`.
- AGP 8.7.3, Kotlin 2.0.21, Compose BOM 2024.10.01, Gradle 8.9, JDK 21.
- Для текста снимаются три снимка (`llama_state_seq_get_data`): системный
  блок, префикс промпта (без последнего токена) и состояние после генерации
  вместе со сгенерированными токенами. Следующий промпт сначала пытается
  продолжить полный снимок, затем префиксный, затем системный. Для рекуррентных
  моделей (LFM3) принимается только чистое продолжение сохранённого префикса,
  иначе промпт обрабатывается целиком.
- Базовый снимок — это только system prompt, инструкции инструментов и
  инструкция размышлений. Он снимается на границе системного блока во время
  первого же префилла (эти токены всё равно считаются) и асинхронно пишется в
  `filesDir/prompt_cache/base-<hash>.bin`. Формат файла: `magic + version +
  32-байтный fingerprint + число токенов + размер состояния + эффективные
  kv/Flash Attention/n_ctx + сырое состояние KV`.
- Fingerprint включает имя, размер и mtime модели, mmproj, `n_ctx`, тип KV,
  Flash Attention, system prompt, инструкции инструментов и бюджет размышлений.
  При несовпадении файл удаляется и строится заново; эффективные kv/FA/n_ctx
  дополнительно проверяются в заголовке. Хранится не больше трёх файлов, старые
  удаляются по LRU.
- Базовый снимок не удаляется при промахе и общий для всех чатов. Медиа-вложения
  по-прежнему очищают текстовый KV, но файл базового кэша остаётся.
- Два RAM-снимка (prompt и full) суммарно ограничены 256 МиБ; при нехватке места
  остаётся только префиксный. Медиа-вложения инвалидируют текстовый кэш, потому
  что позиции `mtmd` не совпадают с токенным префиксом.
- Размышления не сохраняются в контексте: в промпт для завершённых ответов и
  промежуточных шагов tool-loop уходит только видимый текст после закрывающего
  тега. Поэтому у LFM3-1.7B (он генерирует thinking даже при бюджете 0) полный
  снимок не совпадает с очищенным промптом и автоматически используется
  префиксный — это ожидаемый fallback, а не ошибка.
- По умолчанию генерация идёт в 2 потока, обработка промпта — в 4: на
  Snapdragon 695 8 потоков перегружают little-ядра и дают в 2–3 раза меньшую
  скорость. Промпт обрабатывается чанками по 256 токенов; `n_batch=512`,
  `n_ubatch=512`, Flash Attention `auto`, контекст 4096.
- `llama_decode` получает abort-callback, поэтому остановка работает и во время
  обработки длинного промпта.
- Release собран с `isMinifyEnabled`/`isShrinkResources`; JNI-классы и методы
  колбэков сохранены правилами в `app/proguard-rules.pro`.

## Проверено на устройстве

- Huawei RMO-NX1 (HONOR/nova), Android 13 (SDK 33), arm64-v8a, 8 ядер, 7.3 ГБ RAM.
- `LFM3-Omni-2B-Q4_K_M.gguf` (1.02 ГБ) + `mmproj-LFM3-Omni-2B-Q4_K_M.gguf`
  (278 МБ): загрузка ~9 с, генерация ~8–9 tok/s, обработка промпта ~11–25 tok/s.
  Проверены текст, изображение (красный квадрат → «The square is red.») и аудио
  (пример с Wikipedia транскрибирован), а также проигрывание вложения.
- Дополнительно в списке: LFM2.5-8B-A1B, LFM3-1.7B-NVFP4 и qwen 0.8B
  (`context_length=262144`).
- Проверены: несколько сессий (создание/переключение/переименование/удаление,
  сохранение после перезапуска), остановка генерации, Markdown и код,
  сворачивание/разворачивание размышлений, прокрутка вверх во время стриминга,
  реальный cap контекста `128000` и предупреждение о нехватке RAM, импорт через
  SAF, многоходовой диалог, кириллица.
- На LFM3-1.7B (GSQ IQ4_XS, 4096 контекста) префиксный кэш восстанавливает
  десятки токенов между ходами; снимки занимают 2–5 МиБ. Полный снимок с
  ответом сохраняется, но у этой модели thinking вырезается из следующего
  промпта, поэтому срабатывает префиксный fallback. Для моделей без thinking
  полный снимок переиспользует и ответ.
- `llama-bench`, LFM3-1.7B, 128 токенов генерации: 2 потока — ~7.7 tok/s,
